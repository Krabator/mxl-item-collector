# Interface graphique — documentation technique

Fonctionnement de l'IHM de l'éditeur d'objets Median XL (`mxl_gui.py` et modules associés).
Ce qui reste à faire est dans `roadmap.md` (fichier de suivi unique).

## Choix techniques
- **Tkinter + ttkbootstrap** : Tkinter est fourni avec Python, ttkbootstrap lui donne un look moderne (thèmes clairs / sombres).
- Installation (une seule fois, sur le PC) : `pip install ttkbootstrap`
- L'IHM s'appuie sur le code existant (`mxl_data.Data`, `mxl_save.parse_stash`, `mxl_rules.stat_label`, `mxl_rules.stat_range`…) sans le dupliquer.
- Infobulles (28/09) : texte des stats `mxl_stat_text.py`, infobulle d'un objet et règles communes `mxl_tooltip.py`, infobulle du catalogue `mxl_catalog_tooltip.py` (dépendances dans ce sens seulement) ; rendu dans une zone de texte : `mxl_tooltip_view.py`.
- Code : `mxl_gui.py` (lancement : `python mxl_gui.py [fichier.stash]` ; sans argument, **rouvre le dernier personnage et le dernier coffre choisis**, voir « Personnage et coffres »). Réglages de l'utilisateur (langue, personnage et coffre choisis, dossier du jeu, priorités, regroupement par set) : `settings.py`, fichier `settings.json` à côté du programme lancé depuis les sources, dans `%LOCALAPPDATA%\MXL Item Collector` pour l'exécutable (`paths.py`, non versionné) ; écriture sûre depuis le 28/09 (fichier temporaire puis remplacement, copie de la dernière version dans `settings.json.bak`, relue si le fichier est illisible ; fichier abîmé gardé dans `settings.json.broken`, jamais écrasé sans copie) ; les tests utilisent un fichier temporaire (variable `MXL_SETTINGS`).
- **Dossier du jeu et données** (27/09) : au premier lancement, l'éditeur demande le dossier d'installation de Median XL (réglage `game_dir`, bouton « Game folder… » en haut à droite, à côté de la version des données « Median XL 2.14.4 »). Au lancement, si `data/` manque, a été extrait par une ancienne version de l'éditeur (pas d'empreinte) ou ne correspond plus à l'installation (nouvelle version du mod), l'éditeur propose de le reconstruire (fenêtre de progression : tables puis icônes, environ 15 s) ; un refus est retenu jusqu'au prochain changement du jeu (`data_declined`). **Contrôle du contenu** : `install.json` contient aussi la liste des fichiers extraits (taille + md5) ; au lancement, contrôle rapide (chaque fichier présent avec la bonne taille, 0,02 s) ; avec le bouton, contrôle complet (contenu, environ 1 s) ; fichiers absents ou modifiés = « tables incomplètes ou abîmées : n fichier(s) (exemples) », **réparation** proposée à **chaque** lancement tant que data/ n'est pas réparé (refus non retenu) : si le jeu n'a pas changé, seuls les fichiers absents ou abîmés sont ré-extraits (environ 1 s), chacun vérifié par son md5 avant de remplacer l'ancien (`mxl_install.repair_data`) ; si c'est impossible, reconstruction complète. Après une reconstruction, les fichiers extraits sont eux-mêmes contrôlés avant de remplacer data/. Voir `mxl_install.py`.
- **Jeu ouvert = écriture refusée** (28/09) : le jeu (`Game.exe`) garde le coffre en mémoire et le réécrit à sa fermeture ; toute écriture de coffre (déplacement, édition, transfert vers la collection, sortie, restauration, ligne de commande) est refusée avec un message tant qu'un `Game.exe` du dossier de Median XL tourne (`mxl_game.py`, liste des processus par l'API Windows, sans dépendance ; `mxl_save.check_game_closed`, appelé par `commit_file` et au début du transfert, avant l'écriture de la bibliothèque). « Game.exe » d'un autre jeu : pas de blocage ; chemin illisible : blocage par prudence.
- Claude Code travaille directement sur le PC de l'utilisateur : il peut lancer l'IHM et en faire des captures pour la vérifier.

## Disposition retenue
| Zone | Contenu |
|---|---|
| Haut | Choix du personnage, bouton Library, version des données, dossier du jeu, langue |
| Ligne des onglets | Pages du coffre (1 à 10), puis « Character stash / Shared stash » |
| Centre | Grille du coffre avec les objets à leur position (x, y) |
| Droite | Détail de l'objet sélectionné : nom, qualité, ilvl, défense / dégâts, stats avec leur plage |

Boutons, bascules, cases à cocher et onglets ne prennent pas le focus au clic (27/09 : pas de cadre en pointillés dessiné dessus ; option `takeFocus` à 0 dans la base d'options de Tk, `mxl_gui.App`) : ils ne sont plus atteints par Tab.

### Version 2 — vraies icônes du jeu (26/09)
- `extract_data.py` décode les icônes (DC6) en PNG dans `data/items/` (845 fichiers, 4 s) : module `mxl_gfx.py`.
- Recherche dans l'ordre du jeu : MPQ de Median XL (icônes propres dans `medianxl-aXRlbXNnZng.mpq` = « itemsgfx »), puis `patch_d2.mpq`, `d2exp.mpq`, `d2data.mpq`. Palette `data\global\palette\act1\pal.dat` (d2data).
- Format DC6 : en-tête 6 × u32, pointeurs de frames, frame = 8 × u32 (flip, largeur, hauteur…) + RLE (0x80 = ligne suivante, bit 7 = pixels transparents, sinon n indices de palette), lignes de bas en haut. Une case = 28 px.
- Icône d'un objet : fichier d'inventaire (weapons/armor/misc @0x20), sauf types à variantes (bagues, amulettes, joyaux, charmes… : itemtypes.bin nombre @0x23, noms @0x24) où le champ « image » de l'objet choisit la variante.
- Grille : icône mise à l'échelle de la case, fond bleu #0e212f, **rouge #380e0e si le personnage ne peut pas utiliser l'objet** (classe, niveau, Force, Dextérité), comme en jeu (couleurs relevées sur capture). Le nom s'affiche si l'icône manque.
- `mpq.py` lit les archives en `mmap` (d2data.mpq et d2exp.mpq font ~250 Mo).
- **Vocabulaire des calques (convention retenue le 26/09)** — l'image d'un objet dans la grille est composée de trois calques **réellement séparés dans le code** : `mxl_gfx.icon_layers` renvoie trois images transparentes {1, 2, 3}, l'IHM les pose comme trois éléments du canevas (tags `calque1`, `calque2`, `calque3`) tous affichés, **sans interrupteur dans l'interface** (choix du 26/09 ; constante `LAYERS_SHOWN` de `mxl_gui_detail.py`, réglage du code uniquement) :
  - **Calque 1** : l'image de l'objet (icône du jeu, sur le fond de la case : bleu, ou rouge si le personnage ne peut pas l'utiliser) ;
  - **Calque 2** : les slots de sertissage **vides** (`gemsocket`), par-dessus le calque 1 — un slot occupé par un objet serti n'est pas dessiné ; le jeu les fusionne en mode « screen » sur l'objet, le calque contient donc les pixels déjà fusionnés, transparent ailleurs ;
  - **Calque 3** : les objets sertis (runes, gemmes, joyaux…), affichés dans les slots, par-dessus le calque 2.
  - **Opacité** : calques 2 et 3 à **50 %** pour garder le calque 1 prépondérant (`mxl_gfx.LAYER_OPACITY`, choix du 26/09).
- **Slots de sertissage (26/09)** : calque `gemsocket.dc6` (data\global\ui\PANEL, 28 × 28, extrait en `data/items/gemsocket.png`) fusionné en mode « screen » sur l'icône (le noir du slot laisse voir l'objet, comme en jeu) ; objets sertis (gemmes, runes, joyaux, avec leur variante d'icône) dessinés dans les premiers slots. Disposition (`mxl_gfx.socket_positions`) : colonne centrée (objets d'une case de large, ou 1 à 3 slots), 3 slots sur 2 × 2 = 2 + 1, 4 = 2 × 2, 5 = X, 6 = 2 × 3, espacement d'une case. ✅ Warp Blade 1 × 3 et Scale Mail 2 × 3 (2 slots) mesurés sur captures ; 3 à 6 slots non vérifiés. En jeu, les slots n'apparaissent qu'au survol ; ici, toujours affichés.

### Déplacement des objets par glisser-déposer (26/09) — première modification depuis l'IHM
- On saisit un objet à la souris (par n'importe laquelle de ses cases), on le glisse dans la même page, on relâche : l'objet est déplacé **et enregistré dans le fichier**.
- Pendant le glissement, surbrillance légère (blanche) des cases où l'objet serait déposé ; rouge si le dépôt est impossible (hors de la grille 14 × 14 ou chevauchement d'un autre objet). Dépôt refusé = rien n'est écrit.
- Écriture dans la même page : `mxl_save.move_item` réécrit x et y (4 bits chacun, position relevée à la lecture : `_pos_bit`), rien d'autre (✅ test sur copie : 2 octets modifiés, objets sertis et stats intacts). Contrôles : grille et chevauchement (`mxl_save.placement_error`, règle unique aussi utilisée pour la surbrillance), fichier inchangé depuis la lecture. **Écriture sûre** (`mxl_save.commit_file`) — garde-fou (27/09) : aucune écriture dans un coffre situé dans le dossier du programme (copies de test de `tests/fixtures`), quelle que soit l'opération (déplacement, édition, transfert, sortie, restauration, ligne de commande) : nouveau contenu écrit dans `<fichier>.tmp`, relu et vérifié, puis sauvegarde `.bak-AAAAMMJJ-HHMMSS` (avant la **première** modification de la session) et remplacement atomique ; si la vérification échoue ou en cas de coupure, le fichier d'origine reste intact. **Seule la dernière sauvegarde horodatée est conservée** (`mxl_save.make_backup`, aussi pour l'édition des stats en ligne de commande) ; les sauvegardes nommées autrement (ex. `.bak-avant-shark`) ne sont jamais supprimées.
- ⚠️ Le jeu doit être fermé (sinon il réécrit le coffre à la sortie).
- **Vers une autre page (26/09)** : pendant le glissement, survoler un onglet pendant 0,6 s (`TAB_HOVER_MS`) bascule sur sa page ; on peut enchaîner autant d'onglets que voulu tant que le bouton n'est pas relâché, puis déposer dans la grille de la page affichée. Relâcher sur les onglets n'écrit rien.
- Écriture entre pages : `mxl_save.move_item` (avec `page=` ; une seule fonction pour tous les déplacements) retire les octets de l'objet (objets sertis compris) de la section de sa page et les ajoute à la fin de celle de la page cible, en réécrivant x / y. ### Section qualité : valeurs à variance (26/09)
- **Lecture seule dans l'application publique** : note « Item quality », étoiles de priorité, curseurs grisés (position de chaque valeur dans sa plage), aucune écriture de valeur. L'édition des valeurs et la copie vers le coffre sont un module complémentaire privé (`mxl_editor`, chargé par `mxl_ext` s'il est présent : points d'accroche `mxl_ext.hook`), absent de ce dépôt.
- Éditable (`mxl_edit.edit_groups`) : défense de base d'une armure dans [min, max] (pas si elle vaut max + 1) ; stats de l'objet issues de ses affixes ou de la sous-qualité Superior (source **B**) ; stats du runeword (**RW**) ; stats des joyaux sertis dans la plage de leurs propres affixes (**J**). Non éditable : tout ce qui a une plage fixe, les gemmes / runes serties, les stats cachées, et **les dégâts innés** (stat 415, « Innate … Damage », calculés sur un attribut du personnage : pas de variance, même si les tables donnent une plage à l'affixe ; règle unique `mxl_rules.is_innate_damage`, écriture refusée même avec `--force`).
- Plusieurs éléments sur une ligne = curseurs indépendants : sources différentes (Shark « Enhanced Damage » : B 35–50 et RW 24–35) ou couple min / max (« Adds 9-13 Fire Damage » : min 7–10 et max 13–18). Les stats liées (17/18, attributs 0 à 3) sont réglées ensemble par un seul curseur.
- Même stat donnée par plusieurs affixes (rares) : plages additionnées, comme le jeu additionne les valeurs.
- Même stat donnée par plusieurs sources qui s'annulent (ex. runeword Lumen Arcana : RW −3 % + rune +3 % « Poison Spell Damage ») : total nul, **ligne non affichée** dans l'infobulle (26/09).
- **Qualité de l'objet** (26/09) : « Item quality: 80% » en tête de la section Édition = moyenne des positions des curseurs, (valeur − min) / (max − min), pondérée par la **priorité** de chaque stat : 0 % = tous au minimum, 100 % = tous au maximum (`mxl_edit.item_quality`). Priorité = étoiles à droite de chaque curseur, clic pour changer : ★☆☆ Low (poids 0,5), ★★☆ Medium (1, par défaut), ★★★ High (1,5). Priorités **communes à tous les personnages** (depuis le 27/09 : mesure de qualité unique, nécessaire à la bibliothèque d'objets ; l'ancien format par personnage est converti), rangées **par profil d'objet** (`mxl_edit.priority_profile`) : **uniques** (`unique:<n°>`, ex. toutes les Jared's Fragmentor), **sets** (`set:<n°>`) et **Superior gris sans objet serti** (`superior:<code>`) partagent un profil, **enregistré à la fermeture de l'application** (`settings.json`, `item_priorities` = {profil: {stat: priorité}}, valeurs Medium non écrites) ; les autres objets (magiques, rares, runewords, objets sertis : combinaisons trop nombreuses) **n'ont pas d'étoiles** : leur qualité utilise les poids par défaut (tous Medium). Une ligne à côté de la qualité rappelle que les priorités sont conservées. Plages entre crochets retirées des curseurs (déjà dans l'infobulle), étoiles alignées en colonne. Dans un profil, clé par stat : `stat:<n°>`, `defense` pour la défense de base. Qualité recalculée après chaque édition et chaque changement d'étoiles. ✅ Jared's Fragmentor : 79,6 % (ED 54 dans 41-60, Max Damage 5 dans 4-6, Crushing Blow 3 dans 2-3, Life on Melee Attack 30 dans 21-30).
- **Auto-affixes à paliers** (26/09, ex. vitesse des bottes « InnateVelocity ») : chaque ligne d'automagic est fixe, la variance vient du **palier** tiré selon l'ilvl (lignes du même groupe, niveau <= ilvl, type d'objet autorisé). Bottes : 10 (niv. 1), 15 (5), 20 (10), 25 (15), 30 (20), 35 (25), 40 (30) ; ex. Heavy Boots ilvl 12 : « +10% Movement Speed [10-20] », curseur aimanté sur 10 / 15 / 20. Écriture : n° d'auto-affixe (11 bits, `_auto_bit`) + valeur des stats du palier ; valeur hors palier refusée même avec `--force` (`mxl_rules.auto_tiers`, `mxl_save.set_auto_tier`). Seulement si la stat ne vient d'aucun autre affixe de l'objet. Règle « niveau du palier <= ilvl » tirée des tables, non vérifiée en jeu.
